# Internationalization, Localization & RTL

AI-generated UI quietly assumes the whole world reads short English left-to-right. Then the
product ships to Germany (text 35% longer), Japan (different line-breaking), or Saudi Arabia
(the entire layout mirrors) and the design breaks — truncated buttons, overlapping labels,
icons pointing the wrong way, dates that mean the wrong day.

You don't need to translate anything to design *for* translation. Building i18n-ready costs
almost nothing up front and is painful to retrofit. Do it by default for anything that might
reach more than one locale.

> **i18n (internationalization)** = designing/building so the product *can* be localized without
> code changes. **l10n (localization)** = actually adapting it to a specific language and region.
> You own i18n in every build; l10n happens per market.

---

## Build i18n-ready (the structural rules)

1. **No hardcoded user-facing strings.** All copy lives in a resource/translation layer keyed by
   locale, never inline in components. This is the foundation everything else rests on.
2. **Never concatenate sentences from fragments.** "You have " + n + " items" breaks grammar in
   most languages. Use full templated strings with named placeholders and proper pluralization
   (a real plural API handles languages with 1, 2, or 6 plural forms).
3. **Don't bake meaning into word order or position.** Other languages reorder; let the
   translation control the full sentence.
4. **Locale-aware formatting** for dates, times, numbers, currency, units, and addresses — use the
   platform's locale APIs (e.g. `Intl.NumberFormat`, `Intl.DateTimeFormat`), never manual string
   building. `1,000.50` vs `1.000,50`; `MM/DD/YYYY` vs `DD.MM.YYYY` vs `YYYY年MM月`.
5. **Unicode end-to-end** (UTF-8), and fonts that actually carry the target scripts (Latin,
   Cyrillic, Arabic, CJK, Devanagari…). A beautiful font with no glyphs for the language is broken.

---

## Design for text expansion (the #1 layout killer)

Translated text is rarely the same length. English → German/Finnish often **+30–40%**; short UI
strings can **double**. CJK is usually shorter but taller. Design so this doesn't break:

- **Never fix the width/height of text containers to the English string.** Buttons, tabs, nav
  items, badges, and labels must grow gracefully.
- Avoid text in fixed-size pills or single-line areas that can't wrap or truncate cleanly.
- Allow wrapping; if you must truncate, truncate with ellipsis *and* keep the full text available
  (title/tooltip) — and never truncate so aggressively the label loses meaning.
- Test layouts with a "pseudo-localization" pass (pad strings ~40% and add accents) to catch
  overflow before real translations arrive.
- Keep line-length and line-height flexible; CJK and tall scripts need more vertical room.

## RTL / bidirectional text (mirror the whole layout)

For Arabic, Hebrew, Persian, Urdu, the reading direction is right-to-left and the **interface
mirrors** — not just the text.

- Set direction at the root: `dir="rtl"` (and `lang`), then let the layout follow.
- **Use logical CSS properties, not physical ones**, so the layout flips automatically:
  - `margin-inline-start/end` (not `margin-left/right`)
  - `padding-inline-start/end`, `inset-inline-start/end`
  - `text-align: start/end` (not `left/right`)
  - `border-start-start-radius` etc. for corners
  - Fl/grid honor `dir`; prefer them over absolute left/right positioning.
- **Mirror directional icons** — back/forward arrows, breadcrumbs, progress, send, next/previous,
  list bullets — they should point the natural reading way. **Don't mirror** things with absolute
  meaning: logos, clocks, media play buttons, checkmarks, most photographs, phone numbers.
- Numbers and embedded LTR runs (URLs, code, brand names) stay LTR *inside* RTL text — let the
  bidi algorithm handle it; don't force direction on mixed content.
- Mirror animations and slide-in directions too (a drawer that enters from the left in LTR should
  enter from the right in RTL).
- Test with a real RTL locale and a native reader; bidi edge cases are easy to get subtly wrong.

```css
/* Physical → breaks in RTL. Logical → flips for free. */
.card { padding-inline: 1.5rem 1rem; text-align: start; }
.icon-next { /* in [dir="rtl"] this should visually point left */ }
[dir="rtl"] .icon-next { transform: scaleX(-1); }
```

## Locale = more than language

A locale combines **language + region** (e.g. `en-US`, `en-GB`, `pt-BR`, `zh-Hant-HK`) and drives
more than translated words:

- **Formats:** date/time order, 12h vs 24h, number separators, currency symbol and placement.
- **Units:** metric vs imperial; paper sizes; first day of week (Mon vs Sun vs Sat).
- **Imagery, color, icons, gestures:** culturally appropriate — a symbol or color can read very
  differently across regions. Be mindful of culture-specific connotations.
- **Names, addresses, phone formats:** don't assume "First/Last," US ZIP, or a fixed address shape.
- **Sorting/collation:** alphabetical order is locale-dependent.

Detect locale from the user's preference (with an explicit switcher), not just IP. Persist the choice.

## Localization workflow (when a market is actually added)

1. **Translate** all strings (and any text baked into images/video).
2. **Adapt** culturally — imagery, color, examples, legal/format conventions.
3. **Format** — dates, numbers, currency, units, addresses to the locale.
4. **Test in-locale** — overflow, truncation, RTL mirroring, formatting, and a native-speaker
   review. Pseudo-localize earlier to catch structural breaks before translation.

---

## Quick checklist

- [ ] No hardcoded user-facing strings; all in a locale resource layer
- [ ] No string concatenation; full templates + real pluralization
- [ ] Dates/numbers/currency/units via locale formatting APIs
- [ ] Text containers expand/wrap; tested with ~40% longer pseudo-text
- [ ] Logical CSS properties (`inline-start/end`, `text-align: start`) — not physical left/right
- [ ] `dir`/`lang` set; layout and directional icons mirror in RTL; non-directional ones don't
- [ ] Fonts include glyphs for every target script; UTF-8 throughout
- [ ] Locale switcher present and persisted; first-day-of-week and formats follow locale
